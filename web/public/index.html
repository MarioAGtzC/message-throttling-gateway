2. Two limits, one rate

There are two limits on the way out. The worker's BullMQ limiter takes at most 100 jobs per 1000 ms, and Mock C's express-rate-limit accepts 100 requests per 1000 ms and answers 429 beyond. Both are fixed windows, but they do not open at the same moment: the worker's window opens with its first job, and Mock C's with the first request it gets after its previous window ended. Rejected requests count in Mock C's window too.

The chart shows three seconds of a backlog with both limits scaled down to 3 per second. Each job takes about 250 ms, and the time a request needs to reach Mock C varies. When a request arrives sooner than the one that opened Mock C's window, it lands in a window that is already full and gets 429, even though the worker kept its limit.

One job at a time

The worker runs with BullMQ's default concurrency: 1: it takes the next job only when the previous one has finished its two database updates and its request to Mock C. So the real rate is min(limit, 1 / time per job).

  • At 5 ms per job: min(100/s, 200/s) = 100/s, and the default burst of 100,000 messages takes 16m 40s.
  • At 20 ms per job: min(100/s, 50/s) = 50/s, and the same burst takes 33m 20s, twice as long.

The live demo assumes each job takes under 10 ms, so the limit is the only bottleneck.

3. Retries and responses

When the request to Mock C does not end in a 2xx, the worker throws and BullMQ retries the job with exponential backoff: retry n waits 2n−1 × the base delay.

    • A 429 adds one to retries and the message stays RETRYING.
    • Any other error answer (a 503, for example) adds one to retries and marks the message FAILED until its next attempt sets it back to RETRYING.
    • After the last attempt fails, the worker marks the message FAILED for good.
    • A wait is a minimum: when it ends, the job goes back to the end of the waiting list, so under a backlog it runs later than the timeline shows.

    4. Idempotency

    Every message carries an id chosen by the sender (Mock A uses a UUID). Before saving, the gateway looks the id up in PostgreSQL, where it is the primary key:

    • Not found: the message is saved as PENDING, one job is queued, and the answer is 202.
    • Found: the answer is 200 and nothing else happens.

    So a sender can safely repeat a request it is unsure about: each id is saved once and queued once, and Mock C gets it once in normal operation. The step-by-step scenario "Duplicate id" walks through it.

    The look-up and the insert are two separate steps. Two requests with the same new id at the same moment can both miss the look-up; the second insert then breaks the primary key and gets 500. It is still delivered once. See section 5.
