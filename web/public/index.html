2. Two limits, one rate

There are two limits on the way out. The worker's BullMQ limiter takes at most 100 jobs per 1000 ms, and Mock C's express-rate-limit accepts 100 requests per 1000 ms and answers 429 beyond. Both are fixed windows, but they do not open at the same moment: the worker's window opens with its first job, and Mock C's with the first request it gets after its previous window ended. Rejected requests count in Mock C's window too.

The chart shows three seconds of a backlog with both limits scaled down to 3 per second. Each job takes about 250 ms, and the time a request needs to reach Mock C varies. When a request arrives sooner than the one that opened Mock C's window, it lands in a window that is already full and gets 429, even though the worker kept its limit.

One job at a time

The worker runs with BullMQ's default concurrency: 1: it takes the next job only when the previous one has finished its two database updates and its request to Mock C. So the real rate is min(limit, 1 / time per job).

  • At 5 ms per job: min(100/s, 200/s) = 100/s, and the default burst of 100,000 messages takes 16m 40s.
  • At 20 ms per job: min(100/s, 50/s) = 50/s, and the same burst takes 33m 20s, twice as long.

The live demo assumes each job takes under 10 ms, so the limit is the only bottleneck.

Measured on Docker, 8 November 2026 (Docker Desktop on Windows, 8 CPUs, docker compose with the default settings): 10,000 messages from Mock A took 135 s from the first request to the last SENT, about 74 per second, where the live demo gives 1m 40s. All 10,000 were SENT and none FAILED; 158 of them were retried after a 429 at a window edge, 165 retries in all. At 74 per second one job took about 13.5 ms on average, retries included, so here the time per job, not the limit, set the rate.

3. Retries and responses

When the request to Mock C does not end in a 2xx, the worker throws and BullMQ retries the job with exponential backoff: retry n waits 2n−1 × the base delay.

    • A 429 adds one to retries and the message stays RETRYING.
    • Any other error answer (a 503, for example), a network error, or no answer within 5 s adds one to retries and marks the message FAILED until its next attempt sets it back to RETRYING.
    • After the last attempt fails, the worker marks the message FAILED for good.
    • A wait is a minimum: when it ends, the job goes back to the end of the waiting list, so under a backlog it runs later than the timeline shows.

    4. Idempotency

    Every message carries an id chosen by the sender (Mock A uses a UUID). Before saving, the gateway looks the id up in PostgreSQL, where it is the primary key:

    • Not found: the message is saved as PENDING, one job is queued, and the answer is 202.
    • Found: the answer is 200 and nothing else happens.

    So a sender can safely repeat a request it is unsure about: each id is saved once and queued once, and Mock C gets it once in normal operation. The step-by-step scenario "Duplicate id" walks through it.

    The look-up and the insert are two separate steps. Two requests with the same new id at the same moment can both miss the look-up; the second insert then breaks the primary key (Prisma's P2002), and the gateway answers it 200 as well. The message is still saved, queued and delivered once.

    5. Known limitations

    These are gaps in the gateway's code today, shown as they are.

    A message can reach Mock C twice

    Intake is idempotent; delivery is not. The worker sends the request and only then marks the message SENT. If Mock C answers 200 for m1 and the update to SENT then fails, because PostgreSQL is briefly down or the worker process dies, BullMQ runs the job again and Mock C gets m1 a second time. Delivery is at least once, not exactly once.

    How would it be fixed?

    The gateway cannot close this alone: there is always a moment between "sent" and "recorded". The usual fix is on the provider side: send the id as an idempotency key and let the provider ignore an id it already delivered. Checking for SENT before sending makes it rarer but does not remove it.

    6. Design decisions

    Why store the message before queuing it?

    PostgreSQL is the record. Once the gateway answers 202, the message exists and GET /messages/:id can report it, whatever happens to the queue. Redis runs with appendonly yes, so queued jobs survive a Redis restart too, except for up to about a second of writes if Redis crashes (it syncs its log once per second by default). The cost is the gap between the two writes: a crash or a Redis error there leaves a row PENDING with no job. A sweep every minute queues again any message PENDING for over a minute, under a job id derived from the message id, so a message whose job is still waiting is not queued twice. The step-by-step scenario "Restart between saving and queuing" walks through it.

    Why throttle at the worker instead of letting Mock C reject?

    Sending at Mock C's rate keeps 429s rare. Every 429 uses a worker slot, adds a retry and makes the message wait at least a second. Set the worker limit above the provider's in the live demo to see the estimated cost.

    Why BullMQ?

    It gives the gateway what it needs on top of Redis: a rate limiter, attempts with exponential backoff, delayed jobs, and jobs that survive a restart. Its limiter is global for the queue, so every worker shares the same 100 per second. A queue in memory would lose the backlog on a crash.

    Why exponential backoff and 5 attempts?

    A 429 clears when Mock C's window ends, within a second, so the first wait of 1 s is usually enough. A longer outage gets 1 + 2 + 4 + 8 = 15 s before the message is FAILED, with the retries spread out instead of hammering the provider. An outage longer than that leaves messages FAILED, and nothing sends them again.

    Is delivery in FIFO order?

    Yes, except for retries. With concurrency: 1 the worker takes jobs in the order they arrived. A retried job waits in the delayed list and then goes back to the end of the waiting list, so it is delivered after messages that arrived later. The step-by-step scenarios show both cases.

    How would it scale to several instances?

    Several copies of Service B can share PostgreSQL and Redis behind a load balancer, which scales intake. Each copy also runs a worker, but BullMQ keeps the limiter's counter in Redis, so all of them together still send at most 100 per second: Mock C's limit is the ceiling. More workers help only when one job takes longer than 10 ms. Simultaneous duplicates become more likely, but the primary key still keeps one copy of each id.
